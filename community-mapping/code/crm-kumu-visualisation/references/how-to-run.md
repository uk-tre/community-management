# How to run the Kumu export pipeline

## 1. Export from Baserow

For each of the four tables, use Baserow's "Export table" as **CSV**
(xlsx export is not available on the free plan),
with no edits afterwards.
Rename each file to the pattern below:

```
baserow-export-People-email-<DATE>.csv
baserow-export-People-stacked-<DATE>.csv
baserow-export-Organisations-<DATE>.csv
baserow-export-Working-Groups-<DATE>.csv
```

Put them in one folder, expected at `private/crm/baserow-export/2026-10-05/`
(relative to the repo root; this is the default input directory).
Do not open and re-save them in Excel or Numbers: the Slack/Jisc design relies on list
order, which direct exports preserve.

Before exporting, check in Baserow that:

- the `flag-comma-error` views are empty (Organisations and Working-Groups);
- no first name or surname held for a public-identifiable person contains a comma;
- no one is affiliated with `**Other` (an organisation or working group not yet
  in the CRM).
  Add the real organisation or group to Organisations / Working-Groups and
  replace `**Other` on the person's row.
  The `**Other` row itself never appears in Kumu.

The pipeline checks all three and stops if any is found (see below).

## 2. Run

From the repo root:

```
python community-mapping/code/crm-kumu-visualisation/scripts/pipeline.py \
    --input-dir private/crm/baserow-export/2026-10-05
```

Options:

```
--input-dir   (default: private/crm/baserow-export/2026-10-05)
--output-dir  (default: the input directory)
--salt-file   (default: private/crm/pseudonym-salt.txt; must stay fixed)
--names-file  (default: <input-dir>/names-for-public-map.csv if present)
--date        (output filename tag; default: the run time, YYYYMMDD-HHMMSS, local time)
--references-dir  (default: the skill's references/ folder; for tests)
```

If the run prints `STOPPED`, nothing was written, and the pseudonymisation
salt was not read.
Rows with a comma in an organisation/group name, rows affiliated with `**Other`,
and People-email rows with a comma in a name that would be shown publicly are
listed together, one line per row (table, row id, name), before anything else runs.
Fix them in Baserow, re-export the CSV(s) and re-run.
This is a hard stop, not a warning, so that problems are fixed at source early.

Read the warnings (also in `kumu-pipeline-report-<timestamp>.txt`):
differing ORCIDs across one person's emails, unconfirmed email links,
unknown organisation or group names, unstacked emails, list-order mismatches.

## 3. Import into Kumu

Drag the workbook onto a Kumu map.
IDs are stable across runs, so re-importing updates rather than duplicates.
Use the internal workbook for RCM's own map and the public workbook for
anything shared.
`references/kumu-display-settings-internal` and `references/kumu-display-settings-public`
hold the `@controls` and `@settings` code for the legend, filters and showcases of each map.
They are generated by each run (see the next section); paste each into its own map's
settings after importing.
Every element filter has a matching showcase; connection type is a filter only,
because Kumu's showcase has no connection target.
The internal map has the legend at the top right (below the zoom, settings and focus toolbars, which must be listed again once a region is defined; `bottom-left {}` hides Kumu's default legend position).
The internal map offers type, consent, Slack, Jisc, career stage and
career role type.
The public map offers type, career stage and career role type, plus the sign-up, contact and
GDPR text (the PIS link, ethics and approval references are in the template).
Slack and Jisc are internal-only fields (the `link-status` field is still in the internal workbook, but has no filter), so they are not on the public map.
For career stage and role type, add the values under the field's Choices list in Kumu
(Fields), as for type.

## Legend limited to types in use

Kumu lists every colour entry named in `element-color: categorize(...)`,
whether or not that type occurs in the data.
So the pipeline generates the entries instead of hard-coding them:

1. Every element has a `type-display` field (not Kumu's reserved `Type`):
   `Person`, the organisation `type`, or the working-group `type`
   (falling back to `organisation-unconfirmed` / `working-group-unconfirmed`, with a warning, when blank;
   see `config.TYPE_DISPLAY_FALLBACK`).
2. `config.TYPE_DISPLAY_COLOURS` maps each value to a colour. The legend is sorted alphabetically (case-insensitive) by the pipeline.
   It is the single source of truth.
3. After the internal elements are built, the pipeline keeps only the values present,
   warns about any value missing from the registry (Kumu would auto-colour it),
   and writes `references/kumu-display-settings-internal` by substituting the
   entries for `{{TYPE_COLOURS}}` in
   `references/kumu-display-settings-internal.template`.

Edit the **templates** (`...-internal.template`, `...-public.template`) for filters, showcases, text, shapes and scale; edit
`config.TYPE_DISPLAY_COLOURS` for colours.
Never edit the generated file: the next run overwrites it.
It is written to the skill's `references/` folder, so it is version-controlled; it holds
type names and colours only, no CRM data.
The shipped copy lists every type; the first real run replaces it.

## Connection types

Each connection carries `connection-type` (`lead`, `member` or `affiliation`, a copy of Kumu's `Type`).
The settings file styles each type with a `connection["connection-type"=...]` block:
lead dark blue solid, member pale blue dashed (Kumu draws it dotted), affiliation grey solid.
It also has a "filter by connection type" dropdown.
The filter uses explicit `option { selector: ... }` entries: a filter on `by: "connection-type"`
with `target: connection` listed "No values found" in Kumu, although the selectors match.
If a new connection type is added in `config.py`, add its option and style block to the template.
Kumu's Showcase control has no connection target, so use the filter.
After adding a column to the workbook, re-import so Kumu picks it up.

Kumu caveats:

- Kumu remembers every value a field has ever held.
  Stale legend entries from earlier imports (for example individual names) persist.
  The pipeline cannot clear them: import into a fresh map, or delete the old elements first.
- <mark>Not yet confirmed in Kumu: that in a clean map the legend follows only the
  named colour entries. Check on the first real import.</mark>

## Schema check

1. Baserow, account, API tokens: create a read-only token scoped to this database.
2. `GET https://api.baserow.io/api/database/fields/table/{table_id}/` with
   `Authorization: Token <token>`, once per table.
3. Strip `available_collaborators`, check descriptions contain nothing sensitive.
4. Compare with `config.EXPECTED_COLUMNS`, update `config.py`, revoke the token.

## Names

Public-identifiable people are labelled `<first> <surname>` from People-email
`name-first-user-nominated` and `name-surname-user-nominated`:
for each part the first non-empty value in sharepoint-id order across the
person's emails (a warning if emails disagree).
Both parts are needed; otherwise the person keeps the pseudonym label with a warning.

### Names file (optional fallback)

A private CSV with columns `baserow-UUID-person,name`.
Used only when Baserow gives no complete name, for **public-identifiable**
people whose email links are single or confirmed.

## Consent in the outputs

- `None`: left off both workbooks (one `None` email, including a bounced one, excludes the
  whole stacked person, including any public clusters split off by unconfirmed email links).
- Consent given on any email covers all of a stacked person's emails; `not-asked` emails say
  nothing; different levels given -> the most restrictive of those given (see `schema.md`).
- Public organisations: shown only if a validated, publicly consenting person is affiliated
  with them (see `schema.md`).
- Bounced emails (`email-bounced` ticked) are ignored; a person with no working email
  is left off both workbooks (see `schema.md`).
- `not-asked` (or blank): internal map only.
- `internal only`: internal map only.
- `public PSEUDONYMISED` / `public IDENTIFIABLE`: both maps, as in `schema.md`.

## Career role type

`email-career-role-type` is a multi-select. Baserow exports it comma-separated,
but two options contain commas, so the pipeline matches against the known list in
`config.CAREER_ROLE_TYPE_OPTIONS` and writes pipe-joined values.
An unknown value is kept as typed with a warning (add it to the list; a new option
containing a comma would otherwise split into fragments).
